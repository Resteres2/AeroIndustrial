# AeroIndustrial 1.0.0

AeroIndustrial is an original Minecraft 1.21.1 NeoForge technology layer designed to make **industrial processing, rotational power and physics aircraft** participate in one production system without copying GregTech, Create or Create Aeronautics machines.

## Core idea: AeroFlux

AeroFlux is a separate internal energy currency. It is not FE/EU and it is not Create stress.

AeroFlux is generated by three different physical sources:

1. **Kinetic capture** — the mod samples the RPM of adjacent Create kinetic block entities.
2. **Industrial capture** — when GregTech CEu is present, adjacent GT block entities are sampled through a reflection-only bridge; no GT classes are hard-linked into the core runtime.
3. **Motion coupling** — the Sky Relay recognizes Sable/Aeronautics moving structures. The Vector Thruster can apply an impulse to the Sable rigid body through an isolated optional bridge.

The design intentionally creates conversion losses and overload. A machine can be powered but still fail to process if its input/output chain is incomplete.

## Original mechanics

### 1. AeroFlux resonance
Rotational speed is not directly converted into an FE-like battery. RPM becomes a limited flow of AeroFlux, then must be stored and consumed by a different class of machine.

### 2. Phase-chain manufacturing
Components are deliberately staged: crystal → foil/coil → lattice → resonance cell → inertial core → conductor → propulsion hardware.

### 3. Motion-coupled industry
The Sky Relay changes behavior when it is inside a Sable moving sub-level. This means a stationary factory and an airborne factory are not equivalent environments.

### 4. Inertial propulsion
The Vector Thruster does not use a conventional fuel tank. It consumes AeroFlux and produces an impulse through Sable's rigid-body physics when installed on an Aeronautics/Sable moving structure.

### 5. Overload state
Machines track an overload counter. Supplying a machine without enough AeroFlux repeatedly drives the counter upward; reaching the configured limit clears its stored AeroFlux and resets processing.

## Integration architecture

Create, GregTech and Aeronautics are **optional at runtime**. The core block entities never directly reference their classes. The optional bridge uses reflection for detection and a separate Sable bridge class for the actual physics impulse. This prevents a missing optional dependency from causing a class-loading crash.

The Create integration is based on the current 1.21.1 `KineticBlockEntity#getSpeed()` API. Create's 1.21.1 source exposes kinetic speed and network state through `KineticBlockEntity`. The Aeronautics stack uses Sable sub-levels and physics; the dedicated Vector Thruster bridge obtains a `RigidBodyHandle` for the containing server sub-level and applies a local impulse.

Target stack:

- Minecraft 1.21.1
- NeoForge 21.1.x

- Create Aeronautics 1.3.2 for 1.21.1

The external dependencies are not bundled into AeroIndustrial.

## Installation

Place `aeroindustrial-1.0.0.jar` into the `mods` folder of a NeoForge 1.21.1 instance. Create, GregTech and Aeronautics/Sable can be installed for the full integration path. The mod can also start without any of those optional mods; only the corresponding bridge functionality will be inactive.

## Development

Requirements:

- Java 21
- Gradle 8.x
- Internet access to resolve NeoForge, Create, Modrinth and GregTech development artifacts

Build:

```text
./gradlew build
```

The release artifact is written to `build/libs/aeroindustrial-1.0.0.jar`.

## Testing checklist

1. Launch plain NeoForge 1.21.1 without Create/GT/Aeronautics.
2. Launch with Create only and connect a Flux Lattice to a kinetic network.
3. Launch with GTCEu only and test the industrial bridge.
4. Launch with Create + Aeronautics + Sable and assemble a moving structure containing a Vector Thruster.
5. Verify the thruster changes the rigid body's velocity.
6. Break/reload machines and verify AeroFlux, progress and inventory persist.
7. Open every machine GUI and verify slot transfer and synced AeroFlux values.
8. Reload recipes with `/reload` and verify the conditional GT recipe is ignored when GTCEu is absent.
9. Test overload behavior.
10. Run a dedicated server and connect a client.

## Known limitation of this source snapshot

This repository was authored in an environment where the external Gradle/Minecraft dependency artifacts were not available locally and outbound package downloads were unavailable. Therefore the source tree and resources are provided, but this environment could not truthfully claim a completed `runClient`/`build` verification or attach a verified production `.jar`.
